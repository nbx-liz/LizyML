## 監視が DRIFTING と判定した理由 —— 動いているのは契約である

**未コミットの編集は、`export_code` を満たすために受理集合を作り直している。**
`export_code` は **H-0095 に 0 回しか現れない**（宣言された消費者は 4 surface と
2 つの `lgb.train` 表明サイトのみ）。**受理集合の定義が、提案が名指していない
第 3 の消費者によって決められている。** しかも `export_code` は
rounds 2-3 監視が PR 1 のスコープ超過として挙げた面と同じである（2 度目の登場）。

**そして範囲限定ラウンドは、範囲限定ラウンドの目的を達していない。**
D9 は基準を明記していた —— 「clean なら閉包が安定した証拠、そのうえで非限定へ」。
**round 23 は自分のスコープ項目 3 つすべてを反証した。**
D9 には「clean でなかった場合」の分岐が無く、**round 24 は記録のないまま非限定で
走った。**

## main context の処置（`policy:main-context-ownership`）

**採用する。3 点とも当方の非である。**

1. **worktree が clean でなかった** — capsule に clean と書いたまま、こちらが並行して
   編集していた。**監視を回している間は編集しない**が正しい。
2. **`export_code` を受理集合の消費者として H-0095 に記録していなかった。**
   path → テキスト化の変更自体は宣言された契約の内側でも正当（wire 保存、受理集合が
   縮む、型が 1 つ減る）だが、**動機は `export_code` だった**。
   → **H-0095 に消費者として明記する補正を書く**。記録の無い契約変更を記録のある
   ものに変える。
3. **D9 の分岐が足りず、round 24 を記録なしに非限定で走らせた。**
   → D9 に「clean でなかった」ことと、そのまま非限定へ進めた判断を追記する。

**そして `14/1518` の陳腐化は、管理者に伝えた説明を訂正する必要がある** ——
「round 16 以降の指摘はすべて意図的に構築された入力を必要とする」は
**round 24 でもはや真ではない**。
