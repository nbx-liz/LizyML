## こちらの説明が誤っていた 2 点（どちらも実測で確認して訂正した）

### 1. **タプルの `in` はハッシュを引かない**

> `any(type(val) is allowed ...)` は適切である。**しかしタプルのメンバーシップは
> ハッシュしない** —— 同一性／等価の比較を使う。呼び出し元が制御するメタクラスの等価は
> メンバーシップを避ける理由として十分だが、**付随するハッシュの説明は偽である。**

**こちらで再現して確認した**:

```
tuple membership:  result: True  -- __hash__ not called
set membership:    __hash__ WAS called
identity predicate: result: False
```

`BLUEPRINT.md` §14.4 の round 23 の記述は **`set`** についてのもので、そちらでは正しい。
`_ALLOWED_CHOICE_TYPES` は**タプル**なので、こちらはその誤った半分を引き継いでいた。
**結論（`in` を避けて同一性で見る）は変わらないが、理由は「呼び出し元が書ける `__eq__`」
だけである。** `search_space.py` の docstring・`HISTORY.md`・`BLUEPRINT.md` §11.3・
テストの docstring の 4 か所を訂正した。

### 2. **`0/54` から「動いている config は存在しない」は出ない**

> **0/54** は、計測器が `22b11b3` で観測した**choice の出現回数**についての妥当な
> 記述的比率であり、そこには**すでに無効な 3 件の出現**も含まれる。
> **一意な config についての比率でもなければ、あらゆる呼び出し元についての証拠でもない。**
> 記録された数値の主張はそのスナップショットを名指しているが、
> **HISTORY のその後の「動いている config は存在しえない」という主張は、
> 測定が立証する範囲を超えている。**

**訂正した。** 2 型が今日すでに `TUNING_FAILED` になることは実測しているが、それは
「この 2 型を使う config が**動いているとは言えない**」という意味であって、
「**そうした config が存在しない**」ことの証明ではない。
