# PR 2 — なぜ 26 ラウンド回して `APPROVE` が出ないのか（2026-09-09、原因解析）

D13 の判断を取る前に、ユーザー指示で**ループが収束しない原因そのもの**を解析した。
すべて実測。新しい欠陥は探していない。

## 結論

**原因は 2 つあり、独立している。片方は実測で除去できる。**

- **原因 A（設計）**: round 4-5 で決めた「**同一層の重複綴りは、値が等しければ許し、
  違えば拒否する**」という 1 行の仕様が、**任意の Python 値についての全域な等価判定**を
  要求している。この 1 つの述語が、この PR の作業量の過半を生んでいる。
  **その許容分岐は、出荷済みの母集団では一度も発火しない**（下記の新規実測）。
- **原因 B（手続き）**: round 21 以降、レビューの問いが「**どんな値でもこの門を破れないか**」
  という**全称命題**になった。全称命題は反例でしか答えられないので、**`APPROVE` は
  原理的に出ない**。原因 A を除いても、残った機構に対して同じ問いを立てれば同じことが起きる。

---

## 原因 A — 1 行の仕様が開いた領域を要求している

### 因果の鎖（すべて記録から）

1. **#264 の本体**は「`fit(params=)` が学習に届かない」1 件（`b97e30c`）。
2. **round 1**: 届いた override を smart params が黙って上書きする → **拒否する**設計を採用。
3. **round 4**: 「一つの層が 1 パラメーターを 2 綴りで書いた」場合に、辞書順で決まるのは
   不可視なので **`CONFIG_INVALID`** で拒否する。
4. **round 5**: しかし `{"learning_rate": 1, "eta": 1.0}` を拒否したのは**誤拒否**だった。
   → **「等しい値なら無害、違えば拒否」**へ訂正。**ここで等価判定が仕様になった。**
5. その等価判定が `values_differ`。**呼び出し元は現在も 2 か所しかなく、どちらも
   まさにこの問い**である:
   - `lizyml/core/_model_factories.py:894`（`check_duplicate_identities` 内）
   - `lizyml/estimators/lgbm/adapter.py:63`（`_pop_by_identity` 内）
6. **round 12 / 13** が再び「誤拒否も欠陥」(DC7) を押し返す → 受理を広げる → 任意
   オブジェクトについて理解すべきことが増える。
7. **rounds 16-20**、直前の修正が書いたコードの欠陥が 5 連続。**5 件すべてが
   `value_equality.py` の中**（H-0095 の「目的」節が自らそう書いている）。
8. **H-0095** はこれに対する処方 —— **入口で値を正規化し、比較の領域を閉じる**。
   つまり **`param_domain.py` は `values_differ` の入力を有界にするために存在する**
   （`value_equality.py:9` の docstring が明示）。**独立した目的を持つ層ではない。**
9. **rounds 21-26** は全部その閉包の中。

### 規模（実測）

| 区分 | 追加行数 |
|---|---|
| `lizyml/`（production） | **+1,916** |
| `tests/` | +5,571 |
| `docs/`（監査記録） | +6,830 |
| `instruments/` + `prompt-templates/` | +1,503 |

production commit **51 件のうち 30 件**が `value_equality.py`（22 回）または
`param_domain.py`（11 回）に触れている。この 2 ファイルは合わせて **728 行**
（157 + 571）で、**production 追加分の 38%** を占め、その全部が
「2 つの綴りは同じ値か」という 1 つの問いのためにある。

**rounds 18-26 の 9 連続は、指摘がすべてこの機構の内側**である
（16 / 17 の finding 1 は状態と報告なので、境界はここ）。

### 新規実測 —— 許容分岐は出荷済み母集団で **0 回**発火する

`values_differ` が `False` を返す（＝等しいので許す）ケースを、**4 surface すべての
呼び出し点**を包んでスイート全体で数えた（instrument はこの run の scratchpad、
2026-09-09、`9731 passed / 278 skipped`）。

```
observed dicts:      adapter 3938 / model.params 919 / fit(params=) 108 /
                     tuning best_model_params 47 / calibration.params 33 / probe 19
one parameter under two spellings: 51
  REFUSED  (different values): 14
  TOLERATED (equal values):    37
```

**37 件の許容の内訳を、それを起こしたテストに帰属させた:**

```
in files this PR added/changed : 37
in pre-existing test files     :  0
producing file: tests/test_core/test_fit_params_override.py  (37/37)
```

**出荷済みのコード・config・テストで、この許容分岐に到達するものは 1 つも無い。**
既存の実測とも整合する:

- round 11: `Firing rate: 0/811 of pre-existing configs carrying model.params`
- round 12: `0/1009 of pre-existing configs carrying model.params`, `0/22 calibration.params`
- round 13: `0/916`, `0/928` / round 14: `0/70` / H-0093: `0/736`, `0/52`, `0/3`

**つまり「等しい値なら許す」は DC6 の形をした許容である** —— 到達可能で正しいが、
実入力の分布がその分岐を選ばない。**その分岐が 30 commit と 728 行を運んでいる。**

### 同じ PR の中に、厳しい側の前例がある

`7f50c59 fix(tuning): refuse two search dimensions that name one parameter` は、
**値を見ずに重複綴りを拒否**している。**厳しい規則はこの PR 内で既に 1 surface に
採用済み**であり、round 5 の許容は制約ではなく**選択**だったことを示す。

### なぜこれが `APPROVE` を止めるのか

許容分岐を維持する限り、`values_differ` は**任意の Python 値**について全域でなければ
ならない。そして「誤拒否も欠陥」なので、**正しくあるには領域を広げねばならず、
証明可能であるには領域を狭めねばならない**。この 2 つは逆向きに引く。広げるたびに
新しい位置が開き、次のラウンドがその位置を見つける。**round 25 指摘 2 と round 26
指摘 1 が「同じクラスの 2 連続」だったのは、この構造の帰結**であって、実装の不注意ではない。

## 原因 B — 問いが全称命題になっている

round 21 以降のレビュー依頼は、実質「**受理集合の外の値でこの門を破れるか**」を問うている。
これは Python の型システム全体を量化する主張であり、**反例が出れば `REQUEST_CHANGES`、
出なければ「見つからなかった」にしかならない。`APPROVE` の出口が無い。**

外部評価（`pr2_situation_assessment.md`）も同じことを別の言い方で述べている ——
「網羅テストは全称命題を確立できないが、実装の議論は支持しうる。**問い方を変えただけでは
解けていない。**」

**原因 A を除いても B は残る。** round 27 を開くなら、問いを
「**宣言した有界な受理集合の内側で、各消費者の要件が各位置で成立しているか**」という
**有限の問い**に置き換える必要がある。

## 副次的な観測（原因ではないが、同じ根から出ている）

- **構造走査が 3 つある**（`normalise_value` の dispatch / `_holds_a_mapping` /
  `_is_unchanged`）。今日は一致するが、一致を保つ機構が無い（**DC3**）。監視が指摘済み。
- **テスト母集団は numpy の型軸だけ導出で、コンテナ形状は手書き**。観測された欠陥クラスは
  まさにコンテナ形状の側で出ている。

---

## この解析が支持しない主張

- 「レビュアーが厳しすぎる」—— 指摘は 26 ラウンド通してすべて再現済みで、すべて本物。
- 「#264 の本体に問題がある」—— rounds 1-15 で決着し、以後 11 ラウンド clean。
- 「もう 1 ラウンドで終わる」—— 指摘数 2→3→2 はレビュー範囲が異なるので減少率ではない。

## 計測の bound

スイートが構築する母集団のみを測った（`9731 passed`）。ユーザーが将来書く config は
測れない。したがって上の 0 は「**この リポジトリが知っている入力に許容分岐は無い**」で
あって、「ユーザーが等しい重複綴りを書かない」ではない。**厳しい規則へ移す場合、
それは振る舞いの変更であり Change Gate 案件**（H-0094 round 5 の決定の改訂）。
