## `APPROVE` が出ない理由（この分析を再導出しないこと）

**24 ラウンドで指摘ゼロのラウンドが 1 度も無い**（累計 **49 件**、すべて再現・修正済み）。

### 根本 — 受入基準が開いた領域の上に立っている

レビューが答えている問いは実質「**この検証を破る値は存在するか**」で、これは
**Python のあらゆるオブジェクト**を渡る全称命題である。**開いた領域に対する
「反例なし」は有限のレビューでは示せない。**

**H-0095（選択肢 F）はまさにこれを閉じるための設計変更だった。**
rounds 21-24 が示したのは、**閉包を Python で実装した以上、「門」が同じ問いの対象に
なっただけ**ということ:

| round | 破られた前提 |
|---|---|
| 21 | `isinstance` は型を特定しない |
| 21 | `np.timedelta64` は `np.integer` のサブクラス |
| 22 | `__module__` は呼び出し元が書ける属性 |
| 23 | **`type(x) in <set>` は同一性ではない**（メタクラスの `__hash__`/`__eq__`） |
| 23 | **`vars(numpy)` は書き込み可能** |
| 24 | 受理した「型」が書ける「値」とは限らない |

fresh-context checker の言語化:

> **Python のどんな名前空間の読み取りも呼び出し元から独立ではない。
> 「呼び出し元が自称できない」は、どんな導出も提供できない性質である。**

**「これで終わり」は 2 回主張して 2 回外している。3 回目を主張しないこと。**

これは**自分の宣言に対する DC7** であり、この run で**宣言を 3 回書き直している**
（r18「何に対しても raise しない」／r20 の NaN 契約／r23「呼び出し元が自称できない」）。
**毎回、コードではなく宣言のほうが間違っていた。**

### こちら側の寄与 — RED 検証の取りこぼしが 6 回

**「テストが別の理由で緑だった」がこの PR で 6 回**。直近 2 例:

- witness をテスト本体で定義すると **import より後**になるので、`__subclasses__()` 走査
  実装でも集合に入らず緑 → **導出関数を witness 定義後に呼び直す**形に書き直した
- path の変換検査を外しても緑（厳密型一致がサブクラスを先に弾く＝**自分が書いた検査が
  到達不能**だった、DC6）→ 検査を削除し、`format(p,"") == str(p)` を固定する形に

**検証不足の修正を出荷し、その取りこぼしを次のラウンドが拾っている分が確実にある。**
